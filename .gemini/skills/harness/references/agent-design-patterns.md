# Agent Design Patterns (Gemini CLI)

## 실행 모드: 서브 에이전트

Gemini CLI에서는 `Agent` 도구로 서브 에이전트를 호출한다. 에이전트 간 직접 통신(TeamCreate/SendMessage)은 지원되지 않으며, 오케스트레이터가 모든 조율을 담당한다.

### 서브 에이전트 (Sub-agents) — 기본 모드

오케스트레이터가 `Agent` 도구로 서브 에이전트를 생성한다. 서브 에이전트는 작업 결과를 오케스트레이터에게만 반환하고 서로 통신하지 않는다.

```
[오케스트레이터] → [서브A] → 결과 반환
               → [서브B] → 결과 반환
               → [서브C] → 결과 반환
```

**핵심 도구:**
- `Agent(prompt, model, run_in_background)`: 서브 에이전트 생성
- `run_in_background: true`: 병렬 실행 (독립 작업에 사용)

**특징:**
- 가볍고 빠름
- 결과가 오케스트레이터 컨텍스트로 요약 반환
- 토큰 효율적
- `run_in_background: true`로 복수 에이전트 병렬 실행 가능

**제약:**
- 에이전트 간 직접 통신 불가
- 오케스트레이터가 모든 조율 담당
- 에이전트가 유휴 상태가 되면 오케스트레이터가 결과를 수집

### 하이브리드 패턴

Phase별로 병렬/순차를 섞어 구성한다.

```
Phase 1: 병렬 수집 (run_in_background=true)
    ├── Agent(researcher-1)
    ├── Agent(researcher-2)
    └── Agent(researcher-3)
               ↓
Phase 2: 순차 통합 (오케스트레이터가 직접 처리)
    └── 오케스트레이터가 결과 읽기 + 통합
               ↓
Phase 3: 단일 검증 (단일 에이전트)
    └── Agent(qa-agent)
```

### 모드 선택 의사결정

```
에이전트들이 독립적으로 작업 가능한가?
├── Yes → 서브 에이전트 (기본값)
│         병렬이면 run_in_background: true
│
└── No (Phase별 특성이 다름) → 하이브리드
                               Phase별 병렬/순차 명시
```

> **핵심 원칙:** Gemini CLI에서는 서브 에이전트가 유일한 멀티 에이전트 실행 모드다. 에이전트 간 실시간 통신이 필요하다면 파일 기반 비동기 전달로 대체한다.

## 에이전트 아키텍처 유형

### 1. 파이프라인 (Pipeline)
순차적 작업 흐름. 이전 에이전트의 출력이 다음 에이전트의 입력.

```
[분석] → [설계] → [구현] → [검증]
```

**적합한 경우:** 각 단계가 이전 단계의 산출물에 강하게 의존
**예시:** 소설 집필 — 세계관 → 캐릭터 → 플롯 → 집필 → 편집
**Gemini CLI 구현:** 각 단계를 순차적 Agent 호출로 구현. 이전 단계 산출물을 파일로 저장 후 다음 에이전트 프롬프트에 경로 전달.

### 2. 팬아웃/팬인 (Fan-out/Fan-in)
병렬 처리 후 결과 통합. 독립적 작업을 동시 수행.

```
         ┌→ [전문가A] ─┐
[분배] → ├→ [전문가B] ─┼→ [통합]
         └→ [전문가C] ─┘
```

**적합한 경우:** 동일 입력에 대해 서로 다른 관점/영역의 분석이 필요
**예시:** 종합 리서치 — 공식/미디어/커뮤니티/배경 동시 조사 → 통합 보고
**Gemini CLI 구현:** 단일 메시지에서 `run_in_background: true`로 N개 Agent 병렬 호출. 완료 후 파일 Read로 결과 수집.

### 3. 전문가 풀 (Expert Pool)
상황에 따라 적절한 전문가를 선택 호출.

```
[라우터] → { 전문가A | 전문가B | 전문가C }
```

**적합한 경우:** 입력 유형에 따라 다른 처리가 필요
**예시:** 코드 리뷰 — 보안/성능/아키텍처 전문가 중 해당 영역만 호출
**Gemini CLI 구현:** 오케스트레이터가 입력을 분류한 후, 해당 전문가 에이전트만 호출.

### 4. 생성-검증 (Producer-Reviewer)
생성 에이전트와 검증 에이전트가 쌍으로 동작.

```
[생성] → [검증] → (문제시) → [생성] 재실행
```

**적합한 경우:** 산출물의 품질 보장이 중요하고 객관적 검증 기준이 존재
**예시:** 웹툰 — artist 생성 → reviewer 검수 → 문제 패널 재생성
**주의:** 무한 루프 방지를 위해 최대 재시도 횟수(2~3회) 설정 필수.
**Gemini CLI 구현:** 순차적 Agent 호출. 검증 결과를 파일로 저장 후 생성 에이전트에 전달.

### 5. 감독자 (Supervisor)
오케스트레이터가 작업 상태를 관리하며 서브 에이전트에 동적으로 작업을 분배.

```
         ┌→ [워커A]
[감독자] ─┼→ [워커B]    ← 오케스트레이터가 상태를 보고 동적 분배
         └→ [워커C]
```

**적합한 경우:** 작업량이 가변적이거나 런타임에 작업 분배를 결정해야 할 때
**예시:** 대규모 코드 마이그레이션 — 오케스트레이터가 파일 목록을 분석하고 워커들에게 배치 할당
**Gemini CLI 구현:** 오케스트레이터가 작업 목록을 파일(`_workspace/tasks.json`)로 관리. 각 워커가 완료 시 파일 업데이트.

### 6. 계층적 위임 (Hierarchical Delegation)
상위 에이전트가 하위 에이전트에 재귀적으로 위임.

```
[총괄] → [팀장A] → [실무자A1]
                  → [실무자A2]
       → [팀장B] → [실무자B1]
```

**적합한 경우:** 문제가 자연스럽게 계층적으로 분해되는 구조
**주의:** 깊이 2단계 이내 권장. 깊어질수록 컨텍스트 손실 증가.
**Gemini CLI 구현:** 1단계는 오케스트레이터 직접 호출, 2단계는 각 팀장 에이전트가 자신의 실무자 에이전트를 서브 에이전트로 호출.

## 복합 패턴

실전에서는 단일 패턴보다 복합 패턴이 흔하다:

| 복합 패턴 | 구성 | 예시 |
|----------|------|------|
| **팬아웃 + 생성-검증** | 병렬 생성 후 각각 검증 | 다국어 번역 — 4개 언어 병렬 번역 → 각각 네이티브 리뷰어 검수 |
| **파이프라인 + 팬아웃** | 순차 단계 중 일부를 병렬화 | 분석(순차) → 구현(병렬) → 통합 테스트(순차) |
| **감독자 + 전문가 풀** | 오케스트레이터가 전문가를 동적 호출 | 고객 문의 처리 — 오케스트레이터가 문의 분류 후 적합한 전문가 할당 |

## 에이전트 타입 선택

Gemini CLI에서 에이전트는 모두 `.gemini/agents/{name}.md`에 커스텀 정의한다.

### 커스텀 에이전트 (권장)

`.gemini/agents/{name}.md`에 에이전트를 정의하면, Agent 도구 호출 시 해당 정의를 프롬프트에 포함한다.

**선택 기준:**

| 상황 | 권장 방식 |
|------|---------|
| 역할이 복잡하고 여러 세션에서 재사용 | **커스텀 에이전트** (`.gemini/agents/`) |
| 단순 조사/수집이고 프롬프트만으로 충분 | **Agent 도구 직접 호출** + 상세 프롬프트 |
| 코드 읽기만 필요한 분석/리뷰 | **커스텀 에이전트** (에이전트 정의에 읽기 전용 지침 포함) |
| 파일 수정이 필요한 구현 작업 | **커스텀 에이전트** |

**원칙:** 가능한 한 모든 에이전트를 `.gemini/agents/{name}.md` 파일로 정의한다. 파일로 존재해야 다음 세션에서 재사용 가능하고 역할·원칙·프로토콜이 명시되어야 품질이 보장된다.

**모델:** 모든 에이전트는 `model: "gemini-2.5-pro"`를 사용한다.

## 에이전트 정의 구조

```markdown
---
name: agent-name
description: "1-2문장 역할 설명. 트리거 키워드 나열."
---

# Agent Name — 역할 한줄 요약

당신은 [도메인]의 [역할] 전문가입니다.

## 핵심 역할
1. 역할1
2. 역할2

## 작업 원칙
- 원칙1
- 원칙2

## 입력/출력 프로토콜
- 입력: [어디서 무엇을 받는지]
- 출력: [어디에 무엇을 쓰는지]
- 형식: [파일 포맷, 구조]

## 에러 핸들링
- [실패 시 행동]
- [타임아웃 시 행동]

## 협업
- 다른 에이전트와의 관계
- 전달받을 파일 경로
- 산출물 저장 경로
```

## 에이전트 분리 기준

| 기준 | 분리 | 통합 |
|------|------|------|
| 전문성 | 영역이 다르면 분리 | 영역이 겹치면 통합 |
| 병렬성 | 독립 실행 가능하면 분리 | 순차 종속이면 통합 고려 |
| 컨텍스트 | 컨텍스트 부담이 크면 분리 | 가볍고 빠르면 통합 |
| 재사용성 | 다른 프로젝트에서도 쓰면 분리 | 이 프로젝트에서만 쓰면 통합 고려 |

## 스킬 vs 에이전트 구분

| 구분 | 스킬 (Skill) | 에이전트 (Agent) |
|------|-------------|-----------------|
| 정의 | 절차적 지식 + 도구 번들 | 전문가 페르소나 + 행동 원칙 |
| 위치 | `.gemini/skills/` | `.gemini/agents/` |
| 트리거 | 스킬 description 매칭 또는 에이전트 프롬프트에서 Read | Agent 도구로 명시적 호출 |
| 크기 | 작은~큰 (워크플로우) | 작은 (역할 정의) |
| 용도 | "어떻게 하는가" | "누가 하는가" |

스킬은 에이전트가 작업을 수행할 때 참조하는 **절차적 가이드**.
에이전트는 스킬을 활용하는 **전문가 역할 정의**.

## 스킬 ↔ 에이전트 연결 방식

에이전트가 스킬을 활용하는 방식:

| 방식 | 구현 | 적합한 경우 |
|------|------|-----------|
| **프롬프트 내 경로 전달** | 에이전트 호출 프롬프트에 스킬 파일 경로 포함 | 에이전트가 스킬 내용을 Read해서 참조 |
| **프롬프트 내 인라인** | 에이전트 정의 내에 스킬 내용을 직접 포함 | 스킬이 짧고(50줄 이하) 이 에이전트 전용인 경우 |
| **레퍼런스 로드** | `Read`로 스킬의 references/ 파일을 필요 시 로드 | 스킬 내용이 크고 조건부로만 필요한 경우 |

권장: 재사용성이 높으면 파일 경로 전달, 전용이면 인라인, 대용량이면 레퍼런스 로드.
